# 技術說明

這一份是 NBeeTv 的技術文件：模擬結果、接收機的行為、幀結構與各項設計上的取捨。專案的介紹、下載與使用方式在 [README](../README.md)。

短波業餘無線電用的窄頻電視（NBTV）軟體：透過 SSB 電台的音訊，收發 96×72 的畫面。
另有一個實驗中的模式給 VHF／UHF 的 FM 語音通道用，畫面是 192×144。
專案在 GitHub 上的名稱是 NBeeTv；程式裡的名稱（`hf-nbtv`、`NBTV`）沿用原來的。

- **調變**：OFDM，佔 352–2648 Hz，每一幀是一張畫面，開頭有同步用的前導符號，模式由接收機自動偵測。
- **畫面的編碼**：類神經網路把畫面直接變成通道上的值（「學習式」的編碼，實驗中），沒有量化也沒有糾錯碼；
  訊號愈弱畫面愈糊，但不會整張收不到。收發兩邊要用同一份模型的權重。
- **四個模式**：模式 14 每張 0.67 秒、模式 12 每張 1.04 秒、模式 11 與 13 每張 2.72 秒（13 用的是大四倍的網路，畫質再高 0.1–0.6 dB）。
  愈慢的模式一張畫面送的值愈多，畫面愈細。命令列工具、macOS 的 app、Windows 與 Linux 的 app 都可以收發。
- **模式 15（實驗中）**：給 VHF／UHF 的 FM 語音通道用的大畫面，192×144、每張 2.72 秒（幀和模式 11 相同，數據機沒有改）。
  FM 的音訊訊雜比高，卡住畫質的是 96×72 這個畫面大小；同樣多的值改送 192×144，明顯比較清楚。它的模型只照訊號好的情形訓練，
  訊號弱時比其他模式差，不適合短波。命令列工具、macOS 的 app、Windows 與 Linux 的 app 都可以收發；只在模擬裡驗證過。
  見下面的「模式 15：給 FM 語音通道用的大畫面」。
- **模式 5、6、7（實驗中）**：同樣是給 FM 用的 192×144 大畫面，但幀裡沒有導頻：FM 的音訊通道在一幀之內不變，導頻可以省，
  同樣的時間多送 2 成的資料。模式 5 用的模型和模式 15 相同，每張 2.29 秒（快 16%）；模式 6 每張 2.88 秒、畫質高 1.4 dB；
  模式 7 每張 4.43 秒、高 3.6 dB。只能用在沒有頻偏、訊號穩定的 FM 語音通道，不能用在 SSB；只在模擬裡驗證過。
  見下面的「模式 5、6、7：沒有導頻的幀」。
- **模式 3、4（實驗中）**：同一種幀裡快的兩個，用的都是大四倍的網路。模式 3 的畫面是 96×72，每張 0.67 秒，和模式 14 一樣快，
  畫質高 1.8 dB；模式 4 是 192×144 的大畫面，每張 1.01 秒，比同樣快的 96×72 畫面放大來看高約 3 dB。模式 4 的運算量約是
  其他大畫面模式的四倍（M4 Max 上解一張約 0.13 秒），核心少的慢電腦可能跟不上。同樣只能用在 FM、只在模擬裡驗證過。
  見下面的「模式 3、4：同一種幀裡快的兩個」。
- **收聽卡網站**（`apps/web/`）：聽眾上傳從無線電錄下來的 WAV 檔，解得出來就發一張有數位簽章的收聽卡。
- 圖形介面先做了 macOS，再照它搬到 Windows 與 Linux（`apps/desktop/`）；之後不排除 iOS 與 Android。

**已經移除的模式**（2026-11-23）：原本另有六個數位模式（OFDM＋LDPC，每張是一張 AV1 影像，編號 0–5）與三個相干類比模式
（直接傳 DCT 係數，編號 8–10）。照片在同樣的播出時間下，學習式的模式在量過的每一種通道與訊雜比都不比類比模式差，訊雜比愈低贏得愈多
（數字見下面「和已經移除的模式比較」），所以把那兩類整個拿掉，連同 LDPC、AV1／AVIF 影像編解碼（libavif）與 DCT 的程式。
最後一個含有它們的版本有標籤 `legacy-modes`，要用可以從版本庫的歷史取回（`git checkout legacy-modes`）。舊版送的數位、類比模式新版不收
（接收機認得出那是別的模式的幀，不會同步，也不會當成畫面），新版也不再發射它們；
模式 11 到 14 的訊號沒有變（同一批測試圖，移除前後送出的音訊逐位元相同），這四個模式新舊版本之間照常互通。

## 建置與測試

需要 CMake 3.20 以上，以及支援 C++20 的編譯器（Xcode 的 clang、g++ 11 以上，或 Visual Studio 的 MSVC）。核心不需要其他函式庫。

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

測試會用到 `models/` 裡的權重檔；全部跑完約兩三分鐘（M4 Max；多半花在模擬收發鏈與類神經網路的推論）。
用 Visual Studio 的產生器時，建置與測試要指定組態：`cmake --build build --config Release`、`ctest --test-dir build -C Release`，
工具在 `build/tools/Release/`。

**安裝與打包**：`cmake --install build --prefix <目錄>` 把命令列工具裝到 `bin/`、權重檔裝到 `share/nbtv/models/`。
設定時加上 `-DNBTV_INSTALL_FLAT=ON` 則全部放在同一層（執行檔旁邊就是 `models/`），整個目錄可以直接打包給別人；
GitHub 上的下載包就是這樣做的（`.github/workflows/build.yml`：Linux 的命令列工具整個靜態連結（`-DNBTV_STATIC_TOOLS=ON`），Windows 靜態連結 C 執行階段；
Windows 與 Linux 的包裡另外有桌面 app；Windows 的包還附了從原始碼建置的 `ffmpeg.exe`，見 [apps/desktop/README.md](../apps/desktop/README.md#windows-的下載包附的-ffmpeg)）。
工具找權重檔的順序是：環境變數 `NBTV_MODEL_DIR` 指的目錄、執行檔旁邊的 `models/`、執行檔上一層的 `share/nbtv/models/`、
建置時專案的 `models/`（`tools/model_file.hpp`），所以從建置目錄直接執行、裝到別處、搬到別台電腦都找得到。

macOS 外殼另外開一個建置目錄，細節見 [apps/macos/README.md](../apps/macos/README.md)：

```sh
cmake -S . -B build-app -G Ninja -DNBTV_BUILD_MACOS_APP=ON
cmake --build build-app
# 同一台電腦要同時開兩個（兩部電台互相收發）：設定時再加 -DNBTV_MACOS_SECOND_APP=ON，會多做出 NBTV 2.app
```

Windows 與 Linux 的桌面 app 加上 `-DNBTV_BUILD_DESKTOP_APP=ON`（設定時會下載 SDL、Dear ImGui、stb），細節見 [apps/desktop/README.md](../apps/desktop/README.md)：

```sh
cmake -S . -B build-desktop -DNBTV_BUILD_DESKTOP_APP=ON -DNBTV_BUILD_TESTS=OFF
cmake --build build-desktop --config Release --target nbtv-gui
```

## 命令列工具

影像一律是二進位 PPM，大小要和模式的畫面相同：模式 3 與 11 到 14 是 96×72，模式 4–7 與 15 是 192×144。可以用 ffmpeg 轉：
`ffmpeg -i 照片.jpg -vf scale=96:72 -pix_fmt rgb24 影像.ppm`（模式 4–7 與 15 用 `scale=192:144`）。
權重檔預設用 `models/` 裡給那個模式的（`--model` 可以換；`models/` 去哪裡找見上面的「安裝與打包」）。

```sh
# 把影像做成可以直接播放給電台的 WAV（模式 11、三幀；--mode 可以是 11 到 15，或 3 到 7）
build/tools/nbtv-tx --mode 11 --call N0CALL --out tx.wav core/tests/data/coffee.ppm core/tests/data/cat.ppm core/tests/data/rocket.ppm

# 送過模擬的短波通道：2 ms／1 Hz 的衰落、訊雜比 14 dB、頻偏 37 Hz、取樣時脈快 40 ppm
build/tools/nbtv-chan --channel poor --snr 14 --offset 37 --ppm 40 tx.wav rx.wav

# 解回來，收到的畫面存成 PPM
mkdir -p out && build/tools/nbtv-rx --out-dir out rx.wav
# 加 --merge：解每一幀之前把前面幾幀收到的值合進來，畫面沒變的地方比較清楚（見「接收端合併最近幾幀」）
build/tools/nbtv-rx --merge --out-dir out rx.wav
# 加 --json：給程式讀的輸出，每一幀一行 JSON（收聽卡網站用的就是這個）
build/tools/nbtv-rx --json --out-dir out rx.wav

# 收到幾幀、標頭解出幾成、畫質的統計（多執行緒）
build/tools/nbtv-sim --mode 11 --channel poor --snr 5,10,15,20 --image core/tests/data/cat.ppm
build/tools/nbtv-sim --mode 14 --channel awgn --snr 0,5,10 --image core/tests/data/cat.ppm
build/tools/nbtv-sim --mode 14 --channel poor --snr 0,5,10 --burst 8 --merge --image core/tests/data/cat.ppm

# 不經過數據機，只看「畫面 → 通道值 → 加 10 dB 白雜訊 → 解回來」這一段（--mode 12 換成 1.04 秒的模型，--mode 13 換成大型的，--mode 14 換成 0.67 秒的）
build/tools/nbtv-learned --snr 10 --out out/learned.ppm core/tests/data/cat.ppm

# 模式 15（給 FM 用的大畫面）：影像要是 192×144；解回來的畫面也是 192×144
ffmpeg -i 照片.jpg -vf scale=192:144 -pix_fmt rgb24 大圖.ppm
build/tools/nbtv-tx --mode 15 --call N0CALL --out fm.wav 大圖.ppm
build/tools/nbtv-rx --out-dir out fm.wav
```

每個工具加 `--help` 會列出全部選項。`nbtv-rx --trace` 會印出同步與解碼的過程。

### 模式 15：給 FM 語音通道用的大畫面（實驗中）

VHF／UHF 的 FM 語音通道和短波很不一樣：音量設對的話，音訊的訊雜比有 30 dB 以上，也沒有短波那種衰落。模式 11 到 14 在這種通道上
畫質一下子就到頂了，而且卡住的不是通道，是 96×72 這個畫面大小：把 192×144 的原圖縮成 96×72 再放大回來，和原圖比只有 27.5 dB，
96×72 的畫面傳得再完美也只有這樣。模式 15 把畫面加大成 192×144。幀和模式 11 完全相同（同樣 7776 個實數、每張 2.72 秒），
所以數據機沒有改；不同的是模型：18 個潛在通道、格子 18×24，只照 10–40 dB 的訊雜比訓練（模型 261125-3）。

不經過數據機，和 192×144 的原圖比（753 張沒有參與訓練的照片小圖；96×72 的模型吃同一張圖縮小的版本，解出來再用 bicubic 放大）：

| 白雜訊的訊雜比 | 10 dB | 15 dB | 20 dB | 30 dB | 40 dB |
| --- | --- | --- | --- | --- | --- |
| 模式 11 的模型（放大） | 25.8 | 26.3 | 26.5 | 26.6 | 26.6 |
| 模式 15 的模型 | 28.1 | 29.3 | 29.8 | 30.1 | 30.1 |

- 30 dB 時每一張都比模式 11 放大的好，97.7% 超過「96×72 傳得完美」的 27.5 dB。真實影片的畫面上差得更多（30 dB 時高 2.4–7.4 dB）。
- 經過完整的收發鏈（`nbtv-tx` → `nbtv-chan` → `nbtv-rx`，白雜訊 30 dB，三張照片小圖）是 25.70、27.92、31.70 dB，
  和不經過數據機時（25.70、27.93、31.72 dB）差不到 0.02 dB。
- 經過模擬的 FM 語音通道（預強調、頻偏限制器、300–3000 Hz 的濾波、FM 調變與鑑頻、去強調；理想化的電台，音量設在限制器門檻下 12 dB）：
  寬頻 FM（頻偏 ±5 kHz）載波雜訊比 40／30／20／12 dB 時，接收機量到的訊雜比是 35／32／24／16 dB，每一張都收到，

### 模式 5、6、7：沒有導頻的幀（給 FM 用，實驗中）

模式 11 到 15 的酬載裡，每 6 個載波有一個導頻，三個符號輪一遍：佔 17% 的格點、29% 的功率。短波的通道一直在變，
接收機要靠它們一個符號一個符號地追。FM 的語音通道不一樣：解調出來的音訊沒有頻偏，電台的音訊濾波器也不會變，
一幀之內通道是固定的。會變的只有兩件事：兩邊音效卡的取樣時脈差一點（訊號一個符號比一個符號晚到或早到），
以及訊號忽強忽弱時雜訊跟著變。這兩件事都不需要導頻，所以模式 5、6、7 把導頻拿掉，酬載的 49 個載波全部放資料：
同樣的時間多 2 成的資料格，每個資料格的功率還高 0.7 dB（導頻省下來的功率）。

**幀的結構**：S0、S1（和其他模式相同，接收機照樣靠它們找到幀、認出模式）、酬載，最後多一個已知的符號（結尾的參考符號）。
結尾的參考符號用的是 S1 的第 0 條序列：它不是任何模式的編號，接收機不會把它當成下一幀的開頭。循環字首與載波都沒有改。
畫面都是 192×144，模型的做法和模式 15 相同，只是一張畫面送的值不一樣多：

| 模式 | 模型 | 一張畫面送的實數 | 酬載符號 | 每張 |
| --- | --- | --- | --- | --- |
| 5 | 261125-3（和模式 15 同一個，18 個通道） | 7776 | 83 | 2.29 秒 |
| 6 | 261126-2（23 個通道） | 9936 | 105 | 2.88 秒 |
| 7 | 261126-1（36 個通道） | 15552 | 163 | 4.43 秒 |

**接收機**（`core/src/receiver.cpp` 的 `process_frame_free`）原本靠導頻做的事，各有替代：

- **通道與時脈漂移**：開頭的 S1 與結尾的參考符號各量一次通道，兩者差的是一個時間差與一個共同的相位，中間的符號照比例內插。
  同一次發射的幀一個接一個，通道不變，所以把前幾幀的估計平均起來（最多 8 幀），時脈漂移也跨幀平均。
  某一幀的參考符號剛好落在訊號最弱的時候（和預測的對不上），那一個就不用，照前幾幀留下的通道與漂移解。
- **訊號在不在、送到哪裡為止**：看每個符號的循環字首和符號的尾巴是不是相同，不必知道酬載放了什麼。
  捕獲時另外要求 S0、S1 除掉已知的序列之後，相鄰載波的通道估計幾乎相同；別種訊號的酬載過不了這一關。
- **每個符號的雜訊**：聽頻帶上方沒用到的頻率（2.7–4 kHz）。那裡只有雜訊，而且和頻帶內的雜訊同進退；每一格先除以它自己
  平常的大小，所以電台的音訊濾波器在那裡壓低多少都無所謂（壓到幾乎什麼都不剩的話就沒有東西可以聽，整幀改用同一個雜訊值）。
  FM 的訊號掉到門檻以下時的喀喀聲能量集中在低頻，那裡聽到的比頻帶內少，
  所以再看收到的總能量：比預期多出或少掉一大截的符號，雜訊另外調高。
- **各個載波的雜訊**（`RxTuning::carrier_noise`，2026-11-27 加的）：上面量的是一個符號裡所有載波平均的雜訊。
  訊號弱到門檻以下時，喀喀聲經過接收機的去加重，同一個符號裡最低的載波比最高的吵十幾 dB；訊號夠強時大致是平的。
  差多少、是什麼形狀，每一台接收機不一樣，所以不假設，從收到的幀自己量：每個載波收到的功率，扣掉訊號在那個載波上的功率，
  剩下的就是雜訊。訊號的總量由循環字首量（循環字首乘上符號尾巴對應的取樣：兩邊的訊號相同、雜訊無關，雜訊不會讓它偏高；
  訊號被雜訊壓掉的符號量到的就少），照通道估計分給各個載波。一個符號只有 49 個值，看不出形狀，所以把吵雜程度差不多的符號
  放在一起量：照那個符號的訊雜比分成四級（6–10、2–6、−2–2 dB 與 −2 dB 以下；愈吵的符號形狀愈斜，10 dB 以上的不量、照舊），
  49 個載波分成 7 段各自平均，再配一條直線；斜率不到自己誤差的兩倍就當成平的。同一次發射裡前幾幀量到的也算進來。
  沒有任何一個數字是照哪一台電台定的：接到哪一台就量哪一台，量到平的就和以前一樣。
- **找訊號之前先把頻譜拉平**（`RxTuning::flatten_search`，同一天加的）：找前導符號（S0 的滑動相關、S0 與 S1 的判定）、
  確認訊號在不在（循環字首）用的幾個相關值，都是照白雜訊設計的；雜訊集中在低頻時，它們全被最低的那幾個載波拖累
  （S1 被一陣雜訊打到時，能量集中在低的幾個載波上，還會被當成「不是 S1」）。所以這幾步改讀一份拉平過的取樣：
  一階的濾波器 y[n] = x[n] − a·x[n−1]，a 取到濾過之後的頻譜重心落在頻帶正中間（1500 Hz），
  由輸入最近一秒延遲 0、1、2 個取樣的自相關直接算出來。算出來不到 0.5 就不動——輸入本來就平（短波，或訊號夠強的 FM），
  這時候和以前逐位元相同。同樣不必知道接的是哪一台電台。它只影響「找」：解調、估通道、解碼用的還是原來的取樣，
  所以 a 跟著輸入變不會動到通道估計。有導頻的模式共用同一段搜尋。
- **照節拍接著收的兩處修正**（同一天）：前導符號被雜訊打壞的幀，靠前幾幀留下的通道與時脈漂移照樣收得下來，
  但有兩條規則會讓它白白少掉。（一）一幀收完時，「幀尾附近有很像 S0、還來不及判定的東西」就不算完整，下一幀不再照節拍接著收。
  有導頻的幀只能這樣猜這一幀有沒有在尾端被別的發射蓋掉；這種幀不必猜，結尾的參考符號對得上就是送到最後了。
  而且那個門檻不高：實機的錄音裡，七成的幀收完時都有這樣一個候選等著，這個條件等於沒有鑑別力。現在只看結尾的參考符號
  （候選的位置不會漏掉：這一幀收完之後，搜尋本來就會從幀尾之前重新掃一次）。（二）正照節拍收某一幀時，搜尋又找到那一幀自己的前導符號
  （當初沒確認到的那一個），原本會當成新的一次發射重新開始：前幾幀累積的通道、時脈差都丟掉，只靠這一個多半已經被打壞的前導符號，
  標頭常常就解不出來，後面兩三幀跟著沒有。現在同一個模式、幀起點相差不到半個循環字首的，當成確認，接著收。
- **頻偏**：一律當成 0。FM 解調出來的音訊沒有頻偏；而且這種幀一點頻偏都禁不起：頭尾兩個參考符號之間相位只要轉超過半圈就接不起來，
  2.3 秒的幀只容許 0.2 Hz。所以**不能用在 SSB**。

**限制**：

- 真的電台只試過一對（模式 5、6，見下面「經過真的電台」），模式 7 還沒有。真實的電台如果有音訊的自動增益、壓縮或降噪，
  音訊通道可能在一幀之內就變，這種幀就會比模式 15 差；模式 15 有導頻，不受影響。試過的那一對沒有這個問題。
- 不能有頻偏（不能用在 SSB），也禁不起短波那種衰落。
- 整次發射的第一幀只能靠它自己的兩個參考符號；它的前導符號剛好落在訊號最弱的時候就收不到（有導頻的模式也一樣）。
- 沒有配「合併最近幾幀」用的權重。
- 還可以再快一點：模擬裡保護間隔從 5.3 毫秒縮到 4 毫秒也夠用（每張再快 5%），沒有做。

模式 6、7 的模型怎麼來的、以及這種幀做進核心之前的試驗，見 [tools/learned/README.md](../tools/learned/README.md)。

#### 經過真的電台（2026-11-27）

這種幀第一次經過真的 FM 電台，上面「各個載波的雜訊」那三條就是照這一批錄音改的。

**錄到的是什麼**：一對電台，發射端固定（app 的定時發射，每 5 分鐘一次，每次同一段 3 分 42 秒的影片），
接收端帶著移動，用電台自己的錄音功能錄下解調出來的音訊（8 kHz、16 位元），事後轉成 12 kHz 交給 `nbtv-rx`。
一共四趟、七個檔、兩小時：三趟是模式 6（每次發射 78 張），一趟是模式 5（十次發射、每次 97 張）。訊號從很強
（載波在、還沒調變的那 0.3 秒量到的訊雜比是 54 dB）到完全淹在雜訊裡都有；訊號弱的時候雜訊一陣一陣的，是移動中的快速衰落。
錄音是個人的檔案，沒有進版本庫；分析與比較用的程式也沒有。

**這條通道**：頻率響應在 500–1700 Hz 之間差不到 1 dB，375 Hz 低 3.3 dB，2625 Hz 低 5.5 dB；沒有頻偏；
兩邊的取樣時脈差不到 1 ppm；沒有削波。音訊的自動增益、壓縮這些沒有看到痕跡：訊號夠強的幀，頭尾兩個參考符號和前幾幀留下的通道都對得上。

  改前改後收到的張數、標頭正確的比例、PSNR 都相同。沒有導頻的模式在白雜訊下，模式 5 的 5 種與模式 3 的 3 種條件裡各有一種差一張
  （模式 5、−2 dB：30 張裡收到 9 張變 10 張；模式 3、0 dB：60 張裡標頭正確的 59 張變 58 張），PSNR 相同。

**還不知道的**：只有一對電台、一種接收機；別的廠牌訊號弱時雜訊應該也偏低頻（那是 FM 解調加上去加重的結果），形狀會不一樣，
量法是照「不假設形狀」做的，但沒有第二台的錄音可以對。發射端的音量（頻偏）設得對不對，從錄音看不出來。
2650 Hz 以上的頻率響應這批錄音看不到。模式 3、4、7 與有導頻的模式 15 還沒有經過電台。

### 語音與畫面共用 FM 語音通道（實驗中）

一邊送畫面、一邊送即時的語音，兩者擠在同一個 FM 語音通道裡。做法是把通道的音訊頻帶切成兩段：

| | 頻率 | 內容 |
| --- | --- | --- |
| 語音 | 360–1220 Hz | [FreeDV](https://freedv.org) 的 RADE V2（類神經網路的語音編解碼加數據機，約 860 Hz 寬），整段移到中心 790 Hz、濾掉頻帶外的部分 |
| 畫面 | 1335 Hz 起 | 原來的數據機訊號**放慢播放**（頻寬跟著變窄）再往上移。標準版面放慢 1.5 倍，佔到 2866 Hz；窄版面放慢 1.8 倍，只佔到 2611 Hz |

數據機、幀的格式、模型都沒有改，任何模式都可以這樣送（app 只對 FM 用的模式開放）；代價是每一張在空中的時間變成 1.5 或 1.8 倍：

| 模式 | 平常 | 標準版面（1.5 倍） | 窄版面（1.8 倍） |
| --- | --- | --- | --- |
| 3（96×72） | 0.67 秒 | 1.00 秒 | 1.20 秒 |
| 4 | 1.01 秒 | 1.52 秒 | 1.82 秒 |
| 5 | 2.29 秒 | 3.44 秒 | 4.13 秒 |
| 15 | 2.72 秒 | 4.08 秒 | 4.90 秒 |
| 6 | 2.88 秒 | 4.32 秒 | 5.18 秒 |
| 7 | 4.43 秒 | 6.64 秒 | 7.97 秒 |

**這種用法只適合 FM**：兩段都是照絕對的音訊頻率放的，通道不能有頻偏，通帶也要夠平。

**核心裡的部分**（`core/src/duplex.hpp`，C API 是 `nbtv_duplex_*`）只做合成與分離：重取樣、搬頻、濾波，不含語音的編解碼器。
發射端把畫面搬到它的頻段、把語音的訊號（8 kHz 的複數、中心 1500 Hz，RADE V2 給的就是這種格式）搬到它的頻段，兩者相加；
接收端反過來，畫面那一段還原成 12 kHz 的取樣交給原來的接收機，語音那一段還原成語音解碼器要的格式。
兩路預設功率相同（語音可以調大調小，`nbtv_duplex_tx_set_voice_gain_db`），整體的大小由「兩路的峰值碰在一起也不超過滿刻度」決定，
所以合成之後不會削波；畫面分到的功率是單獨送的一半。兩個頻段之間留了 115 Hz 的空隙給濾波器的過渡帶，
只有語音時漏到畫面那一路的不到 −58 dB，只有畫面時漏到語音那一路的約 −43 dB（落在語音最外側的載波之外）。

即時收發時另外有兩個開關，讓外殼原來排幀、收尾、取消的流程不必改：`nbtv_tx_set_duplex` 讓發射機直接給「畫面那一半」
（放慢、搬好、音量照比例調好），語音那一半另外做，播放時兩者相加——畫面可以照原來的做法提早好幾秒排好，
語音到要送的那一刻才編得出來；`nbtv_rx_set_duplex` 讓接收機直接收合成的訊號。

**取樣時脈的差**。畫面被移過頻率之後，兩邊音效卡的取樣時脈只要差一點，訊號除了一個符號比一個符號晚到，
整個頻帶還會一起慢慢轉（每晚一個取樣多轉的角度由移了多少 Hz 決定）。有散佈導頻的幀本來就會量殘餘的頻偏；
沒有散佈導頻的幀（模式 3–7）頭尾兩個參考符號之間只要轉超過半圈就接不起來——標準版面下模式 7 在時脈差 100 ppm、
模式 5、6 在 150 ppm 就整段收不到（窄版面移得更多，更早）。接收機其實已經量得到「晚了幾個取樣」，所以只要知道畫面被移了多少
（`RxTuning::band_shift_hz`，C API 的 `nbtv_rx_set_band_shift_hz`；`nbtv_rx_set_duplex` 會自動設好），
就能照比例算出該轉多少、取離它最近的那一圈。設了之後到 ±250 ppm 每一種模式都收得到（模擬）；沒有移過頻率的平常收訊不受影響。

**模擬的結果**（寬頻 FM 語音通道的模型，不是真的電台；語音只看特徵的失真指標，數字愈小愈好，沒有雜訊時是 0.081）：

- 每一幀都收到。和「同一個模式單獨、照原來的速度送」比，畫面的 PSNR 在 C/N 30 dB 時少 0.05–0.2 dB、C/N 12 dB 時少 0.2–0.4 dB，
  其中語音在旁邊造成的不到 0.1 dB，其餘是功率分一半。語音的失真指標是 0.082（C/N 30）與 0.085（C/N 12），和單獨送幾乎一樣。
- 10 Hz 的衰落、平均 C/N 18 dB：語音 0.15–0.16（約等於白雜訊 2 dB 時的品質），畫面和單獨送相差在 ±0.4 dB 內。
- 語音調小對畫面幾乎沒有幫助、對語音傷害很大（同一個情況下小 6 dB 是 0.232、小 10 dB 是 0.364），所以預設同功率。
- 電台音訊上緣很陡時，標準版面在 2800 Hz 少 0.7 dB、2700 Hz 少 2.2 dB、2600 Hz 少 3.3 dB（每一幀仍然收得到）；
  窄版面在 2600 Hz 不受影響。下緣（語音從 360 Hz 起）很陡的高通到 400 Hz 影響不大。
- 語音送出前一定要先濾過：RADE V2 的訊號有 −28 dB 的功率落在畫面的頻帶裡，會讓畫面的接收機偶爾誤判出沒有畫面的幀
  （12 段各 50 秒裡 9 次，濾過之後 0 次）。核心的合成已經這樣做。
- 核心的測試（`core/tests/test_duplex.cpp`）：畫面經過合成與分離之後，PSNR 與量到的訊雜比和直接收完全相同；
  時脈差 ±200 ppm 收得到。和 Python 寫的原型互相解對方做的音檔、經過模擬的 FM 電台（44.1 kHz 的錄音、時脈差 60 ppm、
  C/N 30 與 15 dB、音訊在 2700 Hz 陡降），畫面全部收到，語音的失真指標 0.081–0.091。

**語音的編解碼器**在核心之外的 `voice/`（介面是 `voice/include/nbtv/voice.h`），是選用的：預設只有空殼，
`-DNBTV_VOICE=ON` 才把 RADE V2 編進來（GitHub 上 0.2.1 之後的下載包有編進去）。它用到兩份別人的原始碼，設定時另外取得、
各固定在一個提交並核對 SHA-256（版本與來源寫在 `voice/cmake/sources.cmake`）：
[rade_c](https://github.com/freedv/rade_c)（RADE 的 C 實作，權重編在程式裡）與 [Opus](https://github.com/xiph/opus)
（語音的特徵 LPCNet 與合成 FARGAN 在它裡面；另外要它的模型資料，約 184 MB）。兩者都是 BSD 授權，條文在 `voice/LICENSES/`。
執行檔因此大約多 22 MB。運算量很小（M4 Max 上發射約佔一條執行緒的 0.6%、接收約 1.4%）。

建法：rade_c 只取原始碼來編；Opus 用它自己的 CMakeLists 建成靜態函式庫，只開語音用得到的那一部分（它叫 deep PLC 的那一組）。
不需要 autotools，所以 Linux、macOS、Windows 是同一種建法，設定時也不必另外安裝什麼；細節與幾種處理器各自的設定寫在
`voice/CMakeLists.txt`。三份檔案（共約 280 MB）可以先抓好（`cmake -DOUT=<資料夾> -P voice/cmake/fetch_sources.cmake`），
之後用 `-DNBTV_VOICE_SOURCES=<資料夾>` 指過去，設定時就不必連網路；CI 就是這樣做的。

對照過的：
- 包的那一層和 rade_c 自己的工具：發射端做的訊號交給它的接收工具，失真指標 0.093（它自己的發射工具是 0.096）；
  接收端解出來的語音和它的工具解的波形相關 0.99。
- 這種建法和 rade_c 自己的建法（Opus 用 autotools）：同一台電腦上做出來的訊號與解出來的語音逐位元相同
  （要打開 Opus 的浮點近似，autotools 的建置預設是開的）。
- x86 與 ARM：算出來的數值不完全一樣（Opus 的類神經網路在兩種處理器上用不同的近似），但互相解得開——
  一邊編、另一邊解，兩個方向解出來的語音音量起伏和原來的相關都是 0.95，和同一種處理器自己編自己解一樣。

建置並跑過測試的：macOS（Apple 晶片與 x86_64）、Linux（arm64 與 x86_64，GCC 12）、Windows（x86-64 與 arm64，微軟的編譯器 MSVC）。
Windows 只在 GitHub 的 CI 上建置、執行過（2026-11-27）：單元測試、對著下載包跑下面這一整條命令列流程、桌面 app 的自我測試都通過；
沒有人在真的 Windows 桌面上用過。

```sh

build/tools/nbtv-duplex demux --picture 收到的畫面.wav --voice 收到的語音.iq 合成.wav
build/tools/nbtv-rx --band-shift 1650.5 --out-dir out 收到的畫面.wav   # 該給多少 demux 會印出來
build/tools/nbtv-voice decode 收到的語音.iq 收到的語音.wav
```

macOS 的 app 與 Windows、Linux 的桌面 app 在右側欄都有「同時送語音」的開關（程式裡有語音的編解碼器才出現，
只對 FM 用的模式有作用），兩邊的做法相同：細節見 [apps/macos/README.md](../apps/macos/README.md#同時送語音)，
桌面 app 不一樣的地方見 [apps/desktop/README.md](../apps/desktop/README.md#和-macos-版不一樣的地方)。

語音是即時編出來的，所以兩個 app 送的時候多做兩件事，都是為了對方的接收端：

- **語音來不及的時候，停整數個符號。** 電腦一時忙不過來，語音還沒編出來，送出去的語音就得停一下（畫面不受影響，它早就排好了）。
  RADE V2 的接收端靠符號的節拍（一個符號 20 ms）對時間：停的長度是符號的整數倍，它接著收；不是整數倍，它要重新同步
  （約半秒聽不到），剛好停在結尾前半秒內的話，「結束」的標記也收不到。用命令列工具在隨機的位置停一下試了 40 次：
  整數倍的 40 次都收到標記，不是整數倍的只有 22 次（沒收到的都停在結尾前 0.6 秒以內）；在合成之後的訊號裡停
  （語音被搬過 710 Hz，相位會跳一下）也一樣，80 次都收到。所以輸出在語音的佇列空掉之後，等到停的長度剛好是符號的整數倍才接回去
  （符號的長度問語音模組：`nbtv_voice_symbol_samples`）。
- **「結束」的標記送完才放開 PTT。** 結尾平常留 0.45 秒的靜音給語音收尾；語音比平常晚的時候（上面那樣停過，
  或收尾的那一步晚了）這一段不夠長，app 會補上不夠的靜音，發射晚一點點結束。

這兩件事是 CI 上比較慢的機器抓出來的（測試給語音的方式在那種機器上會讓語音一直斷）；兩個 app 的自我測試現在各有三個步驟專門看它們，
語音模組的測試也檢查「停整數個符號，標記照樣收到」。

**還沒有驗證的**：真的 FM 電台——麥克風音訊路徑的頻率響應（360 Hz 與 2866 Hz 兩端）、限幅、降噪或音訊 AGC，
是最大的未知；語音實際聽起來如何；兩個 app 的這個功能都只跑過不碰音訊裝置的自我測試，真的麥克風與喇叭還沒有用過；
Windows 上只有 CI 執行過（見上面）。
另外，**RADE V2 在 2026 年底還是測試版**：FreeDV 說波形與權重在正式發佈前可能再改（改了之後新舊版本互相聽不到），
也還不建議在空中使用。要不要上空中請自己判斷；換版本時改 `voice/cmake/sources.cmake` 裡的提交編號與雜湊值。

**從錄音裡看到的兩件事**

1. **音訊中途斷開。** 八段裡，相鄰兩幀起點的距離有 37 次不是整數幀（13 分鐘，平均 21 秒一次）。25 次是後面的訊號晚到：
   25 次裡 20 次是 64 個取樣（5.33 毫秒）的整數倍——64 最多（9 次），另有 128、192、320、512、576、768。
   訊號夠強的那幾次看得很清楚：錄音裡有一段剛好那麼長的時間只剩雜訊（訊雜比 8 dB 的那一段，音量掉到前後的五分之一到四分之一），
   之後的訊號原樣接續、整批晚了同樣的長度。另外 12 次是早到：少了 13 到 516 個取樣，其中 5 次也是 64 的整數倍
   （64、128、256，以及兩次 512）。
   5.33 毫秒這個單位是發射那一側來的：那幾次用的發射機是一台從區域網路收音訊的 SDR 電台，電腦上的用戶端程式把音訊切成
   每包 128 個取樣（24 kHz，剛好 5.33 毫秒）送過去。封包晚到的時候，那段時間送出去的是靜音，等到了再接著播——訊號停幾包的時間、之後整批晚到；
   封包沒有到，就少那幾包。電腦到電台那一段當時走的是 Wi‑Fi：無線網路上封包晚幾毫秒到幾十毫秒、偶爾掉一包都是常有的，
   最可能就是它；不過還沒有改成有線對照過，電腦上的用戶端程式與電台的緩衝也還沒有排除。
   用 USB 音效卡接的電台不走這條路（同一個月的 FM 錄音裡一次也沒有），但任何一段會卡的音訊路徑都會有同樣的效果。
   斷在兩幀之間的，接收機本來就會重新找前導符號，前後兩幀都收得到。斷在一幀中間的，之後的符號全部錯位：
   訊號弱一點的時候那一幀整張沒有；訊號強的時候標頭照樣解得出來（它有重複與迴旋碼保護），交出來的畫面卻有一截是壞的。
2. **「幀尾有沒有像 S0 的東西」這個條件等於隨機否決。** 有導頻的幀原來有一條規則：收完一幀時，幀尾附近如果有很像 S0、還來不及判定的
   候選位置，這一幀就不算完整（可能被別的發射蓋掉了）。酬載自己就常常像 S0（偶數格相隔 128 個取樣會重複，導頻都在偶數格；
   畫面的值小的符號裡導頻佔的比例高），這幾段錄音裡一成到六成五的幀收完時都有這樣一個候選等著（看畫面的內容）。標頭解得出來的幀不受影響；
   標頭一沒解出來，那一幀就不交出去，下一幀的前導符號如果又剛好衰落，也不再照節拍接著收。
   沒有導頻的幀在 2026-11-27 已經拿掉同一個條件（見「經過真的電台」）。

**改了什麼**（細節見下面「接收機的其他行為」的「音訊中途斷開」與「訊號弱時照幀的節拍接著收」）：斷在一幀中間的，
等下一幀的前導符號出現、知道差了幾個取樣之後，回頭把那一幀分成前後兩段各自對時再解；幀尾的那個條件拿掉。

**結果**：八段共多交出 28 張（706 → 734）。回頭接回去的有 18 張，其中 14 張的標頭正確；18 張裡 10 張原來沒有畫面，
8 張原來交出來的是有一截壞掉的畫面（接回去之前與之後擺在一起看，壞的那一截變清楚了）。其餘多出來的是拿掉幀尾那個條件之後
交得出來的（訊號最弱的那一段最多，22 → 31 張）。沒有少掉任何一張。

**還剩的**：773 個位置裡還有 39 個沒有畫面。36 個在訊號弱的時候（11-25 那一段，以及 11-27 第一段裡三次掉到 −6 dB 以下的衰落）：
連著幾幀都沒解出來之後失去同步，要等訊號回來重新捕獲。另外 3 個是斷開之後沒有接回去的：兩個斷在前導符號附近、那一幀根本沒有捕獲到，
一個訊號太弱、找不出分界（見下面「音訊中途斷開」的限制）。

### 接收機的其他行為

**只有雜訊**：四小時的純雜訊（四個亂數種子各一小時），接收機沒有一次誤判為同步，也沒有交出任何幀。
一分鐘的音訊約花 1.5 秒的運算時間（M4 Max，一條執行緒；沒有畫面要解的時候核心不會用到別的執行緒）。

**訊號弱時照幀的節拍接著收**（`RxTuning::follow`，預設開；`core/tests/test_link.cpp` 的 `test_follow`）：
訊號弱時最先撐不住的是標頭與前導符號，畫面其實還解得出來——白雜訊 −4 dB 時標頭只有 4% 解得出來，模式 14 的畫面卻還有 17.4 dB。
原本每一幀都要靠自己的標頭或前導符號才算數（標頭正確的幀後面只多撐一幀），標頭一壞，每一幀都得重新通過和捕獲時一樣嚴的前導符號檢查。
現在鎖定之後，上一幀的導頻從頭到尾都很清楚的話，下一幀就算前導符號沒確認到、標頭也沒解出來，只要它的導頻同樣清楚、
S1 也和目前的模式對得上，就照樣當成一幀；訊號一停，導頻不見了就停下來。

連續發射（每次 32 秒上下：模式 14 是 48 幀、模式 12 是 30 幀、模式 11 與 13 是 12 幀）、貓的測試圖，交出畫面的幀佔送出的比例，

  相干值有 0.53）。所以接著收的幀另外要求導頻的能量分散在整個頻帶（最強的 3 個載波佔不到一半；真正的訊號是 13–29%），

  載波的頻率（330–2650 Hz 共 47 個）、強度（比訊號弱 20 dB 到強 10 dB）與訊雜比（−4 到 25 dB）掃過一遍，每個模式 1,880 次發射，
  原來的接收機在模式 12 有 13 次在發射結束後多交出一張不存在的畫面，現在是 4 次（都在 780 與 1736 Hz，和接著收開或關無關）；

  （模式 12、0 dB、載波強 3 dB：282 幀裡原來交出 194 幀，現在 177 幀）；載波比訊號弱的時候沒有差別。

**音訊中途斷開**（`RxTuning::mend_steps`，預設開；`core/tests/test_link.cpp` 的 `test_audio_break`、`test_late_next_frame`；
只做了有散佈導頻的幀）：一幀收到一半，音訊在送到發射機的路上卡了一下（訊號停幾毫秒到幾十毫秒再原樣接續），或哪一頭少了一段取樣，
之後的符號就整批晚到或早到。照原來的對時，斷開之後的符號全部錯位——而導頻「還在」（錯位的符號夾著前後兩個符號，
同樣錯位的兩個符號之間導頻仍然相干），所以光看導頻在不在看不出來。實際的錄音裡 21 秒就有一次（見「經過空中的短波錄音」）。

- 移了幾個取樣不必猜：下一幀的前導符號出現的位置，和「這一幀的起點＋一幀的長度」差多少就是它
  （兩邊取樣時脈的差造成的那一點，照最近幾幀定時修正的平均先扣掉）。差不到 12 個取樣的不管，超過 2400 個（0.2 秒）的不當成這種情形。
- 那一幀照原來的對時與移過之後的對時各解調一次。相隔 3 個符號的兩個導頻（同樣的格子）相不相干，說明那兩個符號的對時對不對得上；
  假設在某個符號斷開——之前的用原來的對時、之後的用移過的——把每一對的相關值加起來，分界找對了每一對都相干。取加起來最大的分界；
  中間來不及對上的符號（訊號停下來的那一個，少了一段時是不見的那幾個）當成沒有收到。前後兩段各自估通道，之後和平常一樣解。
- 算數的條件：接起來之後各對導頻的相關值總和，要比整幀都照原來的對時多 1.5 以上（完整的一對約 0.5–0.9），後段的導頻也要夠清楚；
  然後標頭解得出來，或者那一幀的前導符號當時確認過、接起來之後整幀的導頻清楚而且不是單頻載波冒充的。
  下一幀只是晚了一點才開始（兩幀之間多了空檔）、或上一幀整個被雜訊蓋掉的時候，這些條件都不成立，不會多交、也不會交出假的
  （`test_late_next_frame`：兩個模式、四種空檔、兩種訊雜比共 16 種情形）。
- 解出來了但可疑的幀先留著不交：標頭沒解出來、有一段沒有導頻，或導頻中間有連著三對對不上（跨過斷點的那三對會這樣）。
  下一幀的前導符號在原來的節拍上確認了，就照原樣交出去（晚 0.07 到 0.4 秒）；不在的話補救之後再交；一次發射的最後一幀沒有下一幀
  可以等，最多晚 0.7 秒。讀檔案的程式在音訊結束時要呼叫 `Receiver::finish()`（C API 是 `nbtv_rx_finish`），留著的那一幀才會交出來；
  即時收訊不必。訊號乾淨、標頭也正確的幀不會被留，和以前一樣一收完就交。
- 測試（連續 5 幀、第三幀中途斷開；頻偏 0.7 Hz、取樣時脈差 100 ppm；音訊一次給 480、1024、4800 個取樣結果都一樣）：

- 限制：斷開的長度剛好是 3 個符號（80 毫秒）整數倍的分不出來——導頻的位置每 3 個符號重複一次，兩種對時下每一對都相干，
  找不到分界，那一幀照原樣交（或沒有畫面）。前導符號或酬載開頭十幾個符號就斷開、因此那一幀根本沒有捕獲到的救不回來
  （上一幀收到了、照節拍接下來的幀不受這個限制）。一幀裡斷兩次的、斷在最後 4 個符號裡的不處理。沒有導頻的幀（給 FM 用的模式）
  沒有做：那一批 FM 電台的錄音裡 1,174 對相鄰的幀沒有一次斷開。

  接收機只是不再因此少一張。

**別的模式的幀**（`core/tests/test_link.cpp` 的 `test_foreign_modes`）：S0 與導頻所有的模式都一樣，只有 S1 參考符號隨模式編號而不同。
接收機把 S1 的 16 條序列全部比過，最像的是模式表裡沒有的編號就不收——已經移除的數位與類比模式（舊版的 app 還會送），
或是以後才加的模式。只比自己認得的四條的話，那種幀偶爾會被當成自己的某個模式收下來：60 種情形（五個編號、兩種幀長、
三種訊雜比、後面有沒有接著我們的發射）裡有 2 種誤判為同步、多回報一幀；全部都比之後是 0 種，緊接在後面的發射也都照常收到。
用移除之前的工具實際送出九個舊模式的訊號（不加雜訊與 6 dB），新的接收機一幀也沒有收。

**干擾**（白雜訊之外再加干擾；`nbtv-sim --impulse`、`--tone`）：

- 脈衝雜訊：接收機依導頻殘差找出被打到的符號，把那些符號上的值標成不可靠再交給解碼器。
  模式 11、白雜訊 14 dB、每秒 2 次（每次 20 ms、比訊號強 20 dB）：4 幀全部收到，貓的 PSNR 26.8 dB；
  不做這個估計的話只有 3 幀的標頭解得出來、畫面 21.1 dB（`core/tests/test_link.cpp` 的 `test_impulse_noise`）。
  模式 14、白雜訊 12 dB、每秒 3 次（貓的測試圖）：48 幀收到 41 幀，平均 20.5 dB。
- 頻帶內的單頻載波：模式 14、白雜訊 8 dB，再加一個 1200 Hz、比訊號弱 3 dB 的載波（貓的測試圖），48 幀全部收到，平均 20.9 dB
  （沒有載波時，5 dB 是 20.9、15 dB 是 22.9 dB）。現在的模式只量過這一個頻率。數位模式還在的時候用它的掉幀率量過九個頻率，
  結果和載波的頻率很有關係：落在沒有導頻的奇數格附近的幾個頻率（700、987.5、1000 Hz）特別差，確切的原因沒有查清楚；
  強的窄頻干擾目前還是要靠電台的陷波濾波器。

**發射與發射之間**（`core/tests/test_link.cpp` 的 `test_back_to_back`、`test_interrupted_transmission`）：
一次發射結束後隔任意長度的空檔又有另一次發射（換人、停了再開始），兩次發射的每一幀都要收到，也不能多出不存在的畫面。
測試裡有 45 種模式與空檔長度的組合、16 種「前一次發射送到一半就停」的情形，用的是現在的四個模式。涵蓋的情形有：

- 空檔很短，新的發射落在接收機「假設對方還在送」而多收的那一幀裡，或離原本預期的位置只差幾毫秒。
- 前一次發射送到一半就停。那個不完整的幀的標頭可能還解得出來（它有重複與迴旋碼保護，禁得起少一截），
  解不出來的話不回報失敗、也不當成畫面；接著的發射就算在它「該結束」之前開始，也照樣收得到。
- 兩次發射之間是完全的靜音（取樣全是 0，虛擬音效卡或檔案）。
- 兩個模式的幀完全相同、只差在前導符號（模式 11 與 13）。

接收機的這一部分和畫面怎麼編碼無關，是數位與類比模式還在的時候調出來的；當時另外以 24 組模式與訊雜比的組合、
各 270–1067 種空檔長度（0–5.8 秒）掃過，共 12,335 種情形，只有 1 種沒過（弱訊號本身的極限）。
那次大範圍的掃描沒有用現在的模式重做。

**壞掉或惡意的輸入**（2026-11-25 做安全掃描時加的）：空中來的訊號、別人給的錄音檔都不能信任，接收機不可以因為它們而讀到
不該讀的記憶體、當掉或從此失靈。

- 推進來的取樣裡有非有限值（NaN、無限大）時當成 0，離譜的大值限制在滿刻度的 100 倍（`dsp.hpp` 的 `clean_sample`；
  `core/tests/test_c_api.cpp` 的 `test_bad_samples`）。以前只要一個 NaN，搜尋同步訊號用的滑動平均就永遠是 NaN，之後什麼幀都收不到
  （要重設才恢復），音量、訊雜比、頻譜的讀數也變成非數值。真的音效卡給不出這種值，虛擬音訊裝置與浮點格式的錄音檔可以。
  現在壞值之後下一幀馬上收得到；連續一長串極大的值（被限制在 ±100）之後要等約 6 秒，搜尋用的平均值降下來才恢復。
- 捕獲幀起點、驗證導頻時會讀到緩衝區尾端之外最多 24 個取樣（`search_step` 等的取樣比 `try_acquire` 最多會用到的少），
  真實音效卡範圍內的訊號就能觸發。讀到的是緩衝區自己預留的空間，不會當掉；已經改成等夠了才檢查，
  並且加了編譯期的檢查，把「等多少」和「最多會往後移多少」綁在一起。
- 模糊測試（測試程式不在版本庫裡，用的是 Homebrew 的 clang 與 libFuzzer）：偽造標頭的幀、截斷、重疊、時間滑動、雜訊、NaN、
  極大值，一半的劇本限制在真實音效卡給得出來的範圍；開著位址檢查、未定義行為檢查與 libc++ 的邊界檢查。
  只改掉越界那一處的版本跑了約 5.3 萬份劇本、最後的版本又跑了約 3.2 萬份，都沒有任何記憶體錯誤或檢查失敗，
  最後的版本也不再交出非有限的讀數。權重檔的載入另外試了 1.76 萬種損壞的檔案
  （逐一改檔頭與每個張量的描述欄位、截斷、位元損壞，都補上正確的檢查碼），不是被拒絕就是載入後安全使用。
- 還在的：呼號接受發射端自己不會產生的寫法（開頭或中間的空白）；訊雜比的讀數在數位靜音之類的輸入下會很大（量到 222 dB）；
  幀與呼號沒有任何驗證身分的機制，誰都可以用任何呼號送出畫面。

**沒有細節的畫面**（`test_link.cpp` 的 `test_flat_pictures`）：全黑、全白、純色，或是鏡頭被蓋住時那種只有一點雜訊的黑畫面。
模式 11、12、14，不加雜訊到 12 dB，共 45 種情形，每一幀都收到、標頭正確，畫面還原（最低的一張 39.3 dB）。

做法：前導符號的判定要求 S0、S1 兩者一致（S0 每 128 點重複，單靠它分不出差 128 點的位置）；
收訊時一邊收一邊繼續找前導符號，證據薄弱的幀會被更明確的前導符號取代；失去同步時回頭從「最後確定有東西的位置」重新搜尋。

## 畫面編解碼的速度

核心裡最花時間的是類神經網路的推論：一張畫面的編碼是 7.6 億到 30 億次乘加，解碼是 13 億到 51 億次
（模式 11、12 的模型最少；模式 13、14 每一層加寬一倍，約四倍；192×144 的模式 5–7 與 15 像素是四倍，也約四倍）。
接收端每收完一幀要解一張，發射端每一幀要編一張（app 另外還解一次當預覽）。算一張的時間必須比一幀短，
接收才跟得上、連續發射才接得上；最緊的是模式 14，一幀只有 0.67 秒。

原本的推論只用一條執行緒，內層迴圈靠編譯器自動向量化：arm64 上是 NEON，x86-64 上只有 SSE2（一次 4 個數），
比較慢的 x86 電腦上解一張大型網路的畫面要比一幀還久。2026-11-26 改成下面這樣（`core/src/parallel.hpp`、`learned_kernels.hpp`）：

- **分給幾條執行緒**：每一層卷積切成小塊（16 個輸出通道 × 幾列輸出），由呼叫的那一條執行緒和核心自己開的幾條幫手一起做，
  誰有空誰領下一塊，所以快慢不同的核心（效能核心與節能核心）也分得勻。幫手是整個行程共用的一組，第一次用到時才開。
  預設最多用「邏輯處理器數，不超過 8」條；環境變數 `NBTV_THREADS`（1 是完全不開執行緒）或 C API 的
  `nbtv_set_inference_threads` 可以改。**不管用幾條，結果逐位元相同**：每個輸出值都是同一個內積算出來的，切法只看那一層的形狀。
- **x86-64 上用 AVX2 與 FMA**：內層迴圈另外用內建函式寫了一份（一次 8 個數、乘加合成一個運算），啟動後第一次用到時看 CPU 與作業系統
  支不支援再決定用不用，不支援的電腦照舊走一般的寫法，同一個執行檔兩種電腦都能跑。環境變數 `NBTV_KERNEL=generic` 可以指定不用。
  `nbtv_inference_kernel()` 回報用的是哪一種（`avx2` 或 `generic`）。兩種寫法的分路與求和順序相同，結果只差在乘加有沒有合成一個運算
  （浮點數的末位），遠小於通道的雜訊：和 PyTorch 比，通道值最大差都是 2×10⁻⁶ 到 7×10⁻⁶，畫面每十萬個值裡不到 10 個差一階。
- **GELU 不再呼叫 C 函式庫的 `erf`**（各家的實作速度差很多，一張畫面要算幾百萬次）：誤差函數改用自己擬合的有理式
  erf(z) ≈ z·P(z²)/Q(z²)（|z| ≤ 4 時最大誤差 7.4×10⁻¹⁰；|z| ≥ 4 當成 ±1），整個式子用雙精度算再轉回單精度。
  和精確值最大差 2.4×10⁻⁷，比原本的寫法（4.5×10⁻⁷）還準一點，而且各平台算出來的幾乎一樣。
- 順便改掉兩個慢的地方：核心的一列不是 16 的倍數時（編碼器第一層一列只有 15 個值）原本是一個一個算，現在補零湊成 16 個；
  十六路的累加器求和改成兩兩相加。這兩處讓結果和改之前差在末位（拿一張合成的畫面比，七個模式的模型裡有六個解出來的畫面逐位元相同）。

開發用的 Mac（M4 Max）上每張畫面的推論時間（毫秒，編碼／解碼）：

| 模型 | 原本（一條執行緒） | 現在只用一條 | 現在預設（八條） |
| --- | --- | --- | --- |
| 模式 11、12（96×72） | 27 ／ 51 | 23 ／ 39 | 4.3 ／ 7.2 |
| 模式 13、14（96×72，加寬） | 98 ／ 176 | 90 ／ 154 | 13.5 ／ 23 |
| 模式 5–7、15（192×144） | 113 ／ 205 | 92 ／ 160 | 14 ／ 24.5 |

**x86 的電腦上還沒有量過**（開發用的 Mac 是 arm64，走的是一般的寫法）。AVX2 的那一份只確認了算得對：把核心編成 x86-64、
用 Rosetta 執行（它會轉譯 AVX2 與 FMA），單元測試拿它和「照同樣的規則用純量算」的結果比是逐位元相同，整套和 PyTorch 的對照也通過；
MinGW 的交叉編譯器編出來的組合語言看過（內層是八個 `vfmadd231ps`，沒有多餘的搬動）。MSVC 編出來的沒有看過，也沒有在 Windows 上執行過。
桌面 app 的自我測試（`nbtv-gui --selftest --only loopback`）會印出那台電腦上每個模式發射端、接收端各算一幀要多久，以及用的是哪一種寫法、幾條執行緒。

**來不及的時候**：`nbtv_rx_set_decode_pictures(rx, 0)` 讓接收機先不解畫面——幀照常接收、回報（呼號、幀序號、訊雜比都有，`skipped = 1`），
只跳過最花時間的那一步，同步與追蹤都不中斷，合併最近幾幀也照樣記著那一幀。桌面 app 在還沒處理的音訊積超過 1 秒時用它，
消化到 0.2 秒以下再恢復：很慢的電腦上只是少幾張畫面，不會愈積愈多、愈來愈晚（見 [apps/desktop/README.md](../apps/desktop/README.md)）。

**載入模型**：每一份權重檔載入時都要把整份檔案算一遍 CRC-32（確認檔案沒有壞，也是模型的識別碼）。原本是一個位元一個位元算，
載入的時間有九成花在這裡；2026-11-27 改成查表、一次算 8 個位元組（`core/src/bits.cpp`），算出來的值相同。
開發用的 Mac 上九份權重檔（共 233 MB）全部載入從 1.66 秒降到 0.33 秒，命令列的 `nbtv-rx` 收一個半秒的檔案從 1.8 秒降到 0.35 秒
（它每次執行都把每個模式的模型載入一遍）。兩個 app 與 `nbtv-rx` 仍然是一啟動就載入全部的模型（展開成單精度後約佔 0.6 GB 記憶體），
還沒有改成用到哪個模式才載入哪一份。

## 草案的待定項目在實作裡的取捨

草案標為「待定」的地方，實作時先各取了一個做法，都可以再改。只和數位、類比模式有關的項目（補足格、位元交錯、係數表、幀增益）已經隨著那些模式移除。

| 項目 | 實作的做法 | 位置 |
| --- | --- | --- |
| 導頻 PRBS 的起始狀態 | 全 1（同 DVB-T），以 FFT 格號索引：w[k] = 1（k < 11），之後 w[k] = w[k−9] ⊕ w[k−11] | `core/src/bits.cpp` |
| S0 同步符號 | 25 個偶數格上的二次相位序列 exp(−jπ·i·(i+1)/25)，包絡峰均比 2.6 dB | `core/src/frame_map.cpp` |
| S1 參考符號與模式編號 | 16 條 BPSK 序列，X_m[c] = mask[c]·(−1)^popcount(m & cls[c])；任兩條的內積恰為 ±1，包絡峰均比最大 6.7 dB。現在用的編號是 11 到 15；0–5、8–10 是移除的模式用過的，不再使用。接收機 16 條都比，認出別的編號就不收 | `core/src/frame_map.cpp`、`tools/design/design_preamble.cpp` |
| 前導符號的功率 | S0、S1 的總功率等於酬載符號的平均值（172/3） | `core/src/frame_map.hpp` |
| 導頻加強量 | 3 dB（未另外最佳化） | `core/src/frame_map.hpp` |
| 格點交錯 | 交錯前的第 i 個格點放到位置 a·i mod N（N 是資料格數）。乘數 a 取約 0.31·N、與 N 互質的數：模式 11、13、15 是 1255，模式 12 是 464，模式 14 是 291 | `core/src/modes.hpp` |
| 發射端削波 | 在解析訊號的包絡上削波兩次、各濾掉頻帶外的產物；門檻比平均包絡功率高 7 dB。削波後的調變誤差比約 33–37 dB（以高斯分布的值代替畫面量的） | `core/src/ofdm_tx.cpp` |
| 幀的標頭 | 每一幀開頭的 176 格（交錯之前的順序）：11 位元組（版本與格式 1、幀序號 1、呼號 6、模型識別碼的最低 8 位元 1、CRC-16 2）→ K=7、碼率 1/2 的咬尾迴旋碼 → QPSK，整份重複兩次。格點訊雜比 0 dB 以上幾乎都解得出來，−2 dB 時約四分之三 | `core/src/frame_header.cpp` |
| 呼號的 40 種符號 | 空白、0–9、A–Z、`/`、`-`、`.` | `core/src/callsign.hpp` |
| 模式 11 到 15（草案之外） | 模式 11、13、15 的幀是 100 個酬載符號（每張 2.72 秒；15 的畫面是 192×144，其餘是 96×72），模式 12 是 37 個（1.04 秒），模式 14 是 23 個（0.667 秒）。標頭之後每格放兩個實數（模式 11、13 是 7776 個、多出來的 3 格是 0；模式 12 是 2592 個、多出來的 33 格是 0；模式 14 是 1512 個、多出來的 3 格是 0），最後整幀做格點交錯。模式 13 的幀和 11 完全相同，只差在模型的每一層加寬一倍。每個模式各有自己的模型，核心依「模型的實數個數與第一層的通道數都和模式的相同」來配對（模式 11、12 是 32 個通道，13、14 是 64 個；權重檔不另外記寬度，由張量的形狀看出來），所以發射機與接收機可以同時掛四個模型。實數放進格點之前先照固定的亂數排列打散（核心的 Rng、種子 "LRN1" 的洗牌），一片衰落抹掉的值才會平均分到整張畫面，而不是集中在某幾行。標頭的格式欄是 1（這種排法）；格式或模型識別碼有一個對不上就不交出畫面 | `core/src/learned_frame.cpp`、`core/src/modes.hpp` |
| 各格點的雜訊不一樣大時 | 接收端取各格點雜訊變異數 σ² 的中位數當參考值（夾在解碼器認得的 −6 到 30 dB 之間）告訴解碼器；比參考值吵的格點，收到的值乘上 (1+σ²參考)／(1+σ²)，並把這個比例當成「可靠程度」一併交給解碼器。模型訓練時就有衰落與缺值，知道哪些值不可信；第一版沒有，衰落時會在畫面上畫出不存在的黑塊與點陣 | `core/src/learned_frame.cpp`、`tools/learned/train.py` |
| 標頭壞掉的幀 | 畫面不靠標頭也還原得出來。只有確定收到的是一整幀（前導符號很明確或緊接在一張好的後面、從頭到尾都有導頻、中途沒有出現別的前導符號）才當成畫面交出去，否則頂多回報「有一幀沒解出來」 | `core/src/receiver.cpp` |

與草案不同的地方：

- **畫面的編碼**整個換掉了：草案的數位（LDPC＋AV1）與相干類比（DCT 係數）都已移除，改用類神經網路。
- **取樣時脈誤差**不靠重取樣器修正。±100 ppm 在最長的一幀（2.72 秒）內只漂 3 個取樣，FFT 視窗提前 16 個取樣就容得下，相位的變化由通道估測的時間內插吸收；每一幀開頭再重新定時。
- **參考模型**沒有另外用 Python 寫，通道模擬與統計直接用 C++（`sim/`、`tools/nbtv-sim`）。
- **核心會開執行緒、也用到 SIMD**。草案說核心不開執行緒、運算量很小不需要 SIMD，那是照 LDPC 與 256 點 FFT 估的；
  換成類神經網路之後一張畫面要幾十億次乘加，所以推論那一段分給幾條執行緒，x86-64 上另外有 AVX2 的寫法（見「畫面編解碼的速度」）。
  其餘的部分照舊：工作都在呼叫的那條執行緒上做完才返回，核心不碰音訊裝置。

## 還沒做的

- 實機測試：模式 12、13、14 有經過空中的短波錄音（2026-11-22 到 27，接收端是公開的網路 SDR、事後解的，見「經過空中的短波錄音」），
  模式 5、6 經過一對 FM 電台（2026-11-27，接收端是電台的錄音、事後解的，見「經過真的電台」）；模式 11、15 與 3、4、7 都還沒有
  （模式 3、4、7 與 15 要的是 VHF／UHF 的 FM 電台）。模式 11 的第一版模型在實機上試過（衰落時畫面上會冒出黑塊，所以才有後來的版本），
  現在的模型只用模擬驗證過。短波的錄音都沒有原圖可以比，空中的畫質還沒有量過。
- 發射端的音訊為什麼會斷（短波的錄音裡平均 21 秒一次；單位是那台網路 SDR 電台的音訊封包，5.33 毫秒一包）：電腦到電台當時走 Wi‑Fi，
  最可能是它，但還沒有改成有線對照過。接收機現在會把斷開的那一幀接回去（見「音訊中途斷開」），但斷在前導符號附近的、斷開的長度是 80 毫秒整數倍的、
  沒有導頻的幀都還救不回來；app 自己不經手那些封包（它把聲音交給電台廠商的虛擬音效裝置），發射時看不到、也不會提醒。
- 模型：小塊的鮮豔顏色會變淡；文字與字幕會被抹糊；模式 11、13 在一半以上的值沒收到時偶爾整張壞掉（訓練沒涵蓋到，各要再訓練一輪）；
  模式 12 的模型還沒有試過多訓練。
- 比 2.72 秒更慢、更細的檔位（移除的類比 10 與數位 0–2 是每張 5.39 秒）。
- 更高解析度的檔位（現在只有給 FM 用的模式 4–7 與 15 是 192×144）、呼號的可讀識別（草案的未決事項）。
- 給 FM 用的模式（3–7 與 15）：沒有「合併最近幾幀」用的權重。
  沒有導頻的幀（3–7）還可以再密一點：保護間隔縮到 4 毫秒、頻帶往上加寬（要看電台），都沒有做。
- 模式 4 的運算量：只在 M4 Max 上量過（分給八條執行緒時解一張 0.13 秒，只用一條是 0.67 秒；一幀 1.013 秒）。
  x86 的電腦與核心少的慢電腦上沒有量過；接收來不及時 macOS 的 app 沒有「略過畫面」的做法（桌面 app 有）。
  發射端「預覽另外解」現在只給模式 4 用，別的模式在很慢的電腦上仍然可能接不上下一張。
- 語音與畫面共用 FM 語音通道：真的電台、真的麥克風與喇叭上還沒有試過；Windows 上還沒有執行過（要等 CI 跑過這一版）；
  收發兩邊要自己選一樣的版面（接收端不會自己認）；語音的音量比例、喇叭的音量在 app 裡還不能調。
- 強的窄頻干擾：自動陷波，或是把被干擾的導頻排除在通道估測之外。
- 實機測試之後才能定的東西：收發機濾波器對頻帶邊緣的影響、削波門檻、PTT 的時序。
- Windows 與 Linux 的桌面 app 在真的電腦與電台上的驗證（音效裝置、鏡頭、序列埠的 PTT、Windows 上的 Hamlib、Wayland）。
- 速度：x86 的電腦上實際量（見「畫面編解碼的速度」）；沒有 AVX2 的 x86 處理器（2013 年以前的，以及一部分入門的 Celeron、Pentium）
  走的是靠編譯器向量化的一般寫法，沒有另外用 SSE 的內建函式寫；arm64 的 Windows（MSVC）同樣靠編譯器，沒有用 NEON 的內建函式寫。
  app 發射時每一幀都連預覽一起算（等於多解一次），很慢的電腦上大型網路的模式仍然可能接不上下一張；
  macOS 的 app 接收時解畫面和瀑布圖還在同一條佇列上，也沒有「來不及時先不解畫面」（桌面 app 有）。
